# Download manager rewrite

## Execution path

`DownloadHandler` snapshots available WebView request metadata → foreground-service intent → repository persists the pending item → engine acquires a file permit → one GET supplies headers and data → stream/range workers write disjoint positions → force, close, move → completion.

The filename helper no longer makes requests. HEAD and disposable GET probes are removed. OkHttp 5.5.0 remains the transport: replacing it with Cronet/native curl would introduce native packaging and another transport lifecycle without demonstrated Android-device benefits. The engine uses pooled connections, bounded asynchronous request dispatch, 64 KiB worker buffers, reusable disk ByteBuffers, and coalesced progress/persistence.

A 256 KiB initial sample chooses single-stream operation above 32 MiB/s; slower range-capable sources use size-bounded parallel ranges (maximum eight extra workers). This is a heuristic, not a universal optimum. Ranges are fixed during a worker's lifetime; no disk write holds the task-wide segment lock. If ranges are rejected on a fresh transfer, the original GET continues through the remaining file instead of issuing another full GET. TCP receive-buffer overrides were removed to let the OS autotune.

## Request fidelity and limits

Per-WebView request capture stores at most 64 requests for 60 seconds. The handoff preserves available header values, method, listener user agent, disposition, content length, and cookie snapshot, including private-profile cookies. It does not truncate Referer, fabricate Origin, or force an English language preference. The cache is per WebView, not global.

Android WebView is **not** a full Chrome download interception API. `DownloadListener` does not expose request headers/method/body; `shouldInterceptRequest` does not expose POST bodies or subsequent redirect requests, and its header map cannot represent duplicate header fields. Consequently exact replay of every browser download is impossible through these APIs. Known non-GET requests are refused; blob downloads remain unsupported. Missing metadata is not evidence that the originating request was GET. Sites using renderer-only credentials, client certificates, POST downloads, referrer-policy details unavailable to the listener, or anti-bot TLS fingerprints still need a browser-native transfer mechanism.

Deliberate transport differences:

- `Accept-Encoding: identity` keeps range offsets tied to stored file bytes. Servers ignoring it fail safely.
- Captured cache validators and framing/hop headers are removed: a file transfer must not receive a bodyless 304 or replay browser connection framing. Range/If-Range are generated by the engine.
- Authorization and cookies are stripped on cross-origin redirects and when requesting a cross-origin resolved URL. This avoids leaking source credentials, but destination cookies unavailable from WebView are not synthesized.
- Browser content length is preserved as metadata, not trusted as the authoritative identity-representation size.

Request metadata and validators are persisted in the existing app-private Room database, schema 11. Treat the database as credential-bearing; URLs and headers must not be included in benchmark fixtures or exported diagnostics with real credentials.

## Resume and integrity

Every worker validates status, exact Content-Range start/end/total, body length, identity encoding, and returned resource validator before writes. Resume uses a strong ETag, or Last-Modified only when the response Date is at least 60 seconds later (RFC 9110 validator rule). HTTP 200/416 and mismatches never append to saved bytes. A missing validator, missing/inconsistent range map, or unverified legacy progress fails without deleting the partial file.

Per-segment SHA-256 state is updated after successful writes. Snapshots clone the digest and persist the checksum with the exact byte counter. Process-restart resume streams those saved byte intervals from disk to verify checksums and reconstruct digest state before network transfer. This adds CPU cost and disk-read startup latency, but detects altered files and zero-filled/preallocation holes. It is not a source-provided authenticity checksum, and cannot detect a server that consistently sends incorrect content. Legacy partial files without checkpoints are retained but cannot automatically resume.

Transient IO errors and HTTP 408/429/5xx receive bounded worker retries. Numeric Retry-After is honored up to five minutes; HTTP-date Retry-After is not currently parsed. Existing repository automatic retries remain bounded and no longer reset their budget on every DOWNLOADING transition. Network callbacks pause active transfers when the active network disappears and resume network-waiting transfers after validated connectivity returns.

Pause/resume joins the previous generation before opening another writer. Cancellation/removal waits for workers and cleanup before releasing filename ownership. The file-level concurrency permit covers worker cleanup. Completion checks actual written bytes and file length, forces data, closes the writer, and moves without replacing an existing destination. Failed finalization retains complete partial data for retry. Power-loss durability of the parent-directory entry is filesystem-dependent; directory fsync is not implemented.

Filename handling preserves spaces, dots, case, plus signs, percent text in ordinary disposition filenames, and extensions. RFC extended filenames are decoded once (including charset/language). Only path separators/control characters, filesystem byte limits (250 bytes to leave room for `.part`), collisions, and explicit media-format overrides alter names. Collision suffixes protect unrelated files and concurrent reservations.

## Reproducible comparison

Run from the repository root:

```sh
scripts/download-benchmark/run.sh --offline --rerun-tasks
NEXA_BENCH_DELAY_MS=0 NEXA_BENCH_OUTPUT=/tmp/nexa-fast.csv \
  scripts/download-benchmark/run.sh --offline --rerun-tasks
```

The script compiles baseline engine sources from revision `4b8e290` into an isolated temporary test package alongside the rewrite; it does not switch branches or alter production sources. Sources are deleted on exit. Set `NEXA_BENCH_BASELINE` to compare another compatible revision. The baseline revision must be available in the local Git history.

Fixture: 32 MiB deterministic data, HTTP/1.1 localhost, 20 ms server startup delay, 64 KiB server writes, one warm-up and three measured rounds. Default server delay is 4 ms per write **per connection**, intentionally modeling per-connection throttling. The second fixture removes that delay. All outputs must match the fixture SHA-256. Environment knobs: `NEXA_BENCH_MIB`, `NEXA_BENCH_DELAY_MS`, `NEXA_BENCH_REPEATS`, `NEXA_BENCH_OUTPUT`.

CSV includes completion time, throughput, server-side first-body timestamp, request count, server body bytes, JVM process CPU time, and heap delta. These are not device RSS, real client TTFB, socket-level wire-byte counts, or NIC utilization. Curl runs as a subprocess, so its CPU/memory figures are **not comparable** to JVM process measurements. The server shares the JVM; CPU numbers include fixture work. Heap deltas are GC-sensitive and are not peak memory.

### Measured results

Raw runs are in `scripts/download-benchmark/results/`. Median of three adaptive runs before the final buffer/checksum-allocation cleanup:

| Fixture | Legacy MiB/s | Rewrite adaptive MiB/s | Rewrite forced single MiB/s | curl MiB/s |
| --- | ---: | ---: | ---: | ---: |
| Per-connection delay | 55.32 | 54.65 | 14.73 | 14.64 |
| Unthrottled localhost | 267.23 | 205.44 | 224.48 | 630.14 |

Default delayed-fixture first-body medians: legacy ~44 ms, rewrite ~22 ms. Requests: legacy 5, rewrite 4. Parallel rewrite server body bytes were ~35.5 MB for a 33.55 MB output because the original full GET can have unread bytes in flight. The fixed-parallel experiment sent ~58.7 MB on the unthrottled fixture; adaptive single-stream reduced that to exactly 33.55 MB with one request.

The final delayed-fixture rerun (`final-throttled.csv`) measured median throughput of 55.34 MiB/s for legacy, 54.78 MiB/s for adaptive rewrite, 14.75 MiB/s for forced single-stream, and 14.72 MiB/s for curl; first-body medians were 43.52 ms legacy and 21.55 ms rewrite.

The rewrite is **not faster in every scenario**. It improves initialization/request count and reduces measured allocation, while integrity hashing and force-to-disk can reduce peak localhost throughput. Parallelism outperforms single-stream on the per-connection-throttled fixture but cannot exceed a shared bottleneck. No claim of outperforming IDM/FDM or universally maximizing throughput is supported by these tests.

### References and remaining release validation

- [IDM features](https://www.internetdownloadmanager.com/features2.html): dynamic segmentation, connection reuse and interrupted-transfer recovery. These are vendor behavioral descriptions, not verified comparative numbers.
- [FDM features](https://www.freedownloadmanager.org/features.htm): parallel sections and resume. FDM is installed on this host, but no equivalent automated GUI benchmark was performed. IDM's Windows runtime was not available.
- [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110): sections 8.8, 13.1.5 and 14 for validators, If-Range and ranges.

Before claiming Android production performance parity: benchmark on physical devices (RSS/CPU/storage/network), HTTP/2 and HTTP/3 CDNs, authenticated redirects, one-use links, packet-loss/latency fixtures, large files, disk-full/power-loss cases, and actual IDM/FDM under equivalent shaping. UI and foreground-service quota behavior also need device instrumentation; JVM and lint success cannot establish those guarantees.

## Validation

`./gradlew :app:testDebugUnitTest :app:lintDebug --offline`

The full JVM suite completed with 683 tests, zero failures, and three skipped tests; Android lint passed. The benchmark was also rerun successfully after final engine cleanup.

Critical regression tests cover request preservation, unsafe range responses, weak validators, filename parsing, migration chains, disjoint process-restored ranges/checksums, corruption rejection, unknown-length responses, range rejection fallback, rapid pause/resume, cancellation, and destination collision protection. Existing repository, persistence, settings, and UI-viewmodel tests remain in the suite.
